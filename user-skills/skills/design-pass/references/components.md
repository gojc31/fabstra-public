# Components - step 5(c)

Step 5(c) runs this file at every scope - PAGE, SCREEN, COMPONENT, EXISTING - on OPEN and INHERIT passes alike, whenever the plan has interactive components. It names the stack, picks the best-fitting source for each interactive component from `D:\jc-ui-kit\CATALOG.md`, and writes one line per component into the blueprint's `Components:` slot.

Builders never load skills, so every line carries all of its instructions itself. Write each shape below out in full on the line - its known gaps, keyboard clause, verify walk and licence included - never a pointer back to this file. The slot may open with one `States:` preamble holding the state rules every line shares (focus ring, hover, active, disabled); each line then writes only the states that differ.

## 1. The stack, and what binds on every stack

Name the stack first, from the brief or the project. Three signals, each read on its own:

| Signal | Present when |
| --- | --- |
| **React** | `package.json` lists `react` and the surface renders through it (Next.js, Remix, Vite React). Otherwise name the framework: SvelteKit, Svelte, Nuxt, Vue, Astro, plain HTML |
| **Tailwind** | `tailwindcss` in `package.json`, a `tailwind.config.*`, or `@import "tailwindcss"` / `@tailwind` in the entry stylesheet |
| **shadcn** | a `components.json` at the root of the app or package the UI installs into (shadcn-svelte and shadcn-vue write one too; without React the project still takes section 5) |

A Tailwind signal proves neither React nor shadcn: a SvelteKit or Nuxt app carries the same Tailwind signals. With no project yet and a brief that does not say, ask that one question: which framework, and Tailwind or plain CSS.

| Stack | Section |
| --- | --- |
| React + Tailwind + shadcn | section 2 |
| React + Tailwind, no shadcn | section 3 |
| React + plain CSS | section 4 |
| Any other framework, Tailwind or plain CSS | section 5 |

The blueprint's `Stack:` line names all three signals and where each came from, e.g. `Stack: React + Tailwind + shadcn · from package.json react, @import "tailwindcss" in src/index.css, components.json`.

On every stack:

- **Inherit before invent.** When the project already has its own component for the role, the line is `<component>: inherit <path>`, ahead of every source - on a shadcn project that includes its own shadcn or ReUI components. A native control the project already uses (`<input type="date">`, `month`, `number`, `<select>`) is the incumbent too. On an EXISTING redesign or a restyle, write the restyled form: `<component>: inherit <path>, restyled · restyle: <what changes> · states: <default, hover, focus-visible, active, disabled, loading, error, success> · keep: <every class, id and DOM shape a test or motion hook reads>`. An incumbent that serves the role stays inherit even when it fails a gate as built; the Design block fixes its motion and states. It falls to the next source when it cannot serve the role, or on an **upgrade brief** - one that asks to take a library component where it beats the incumbent. An upgrade brief compares, per role, the incumbent with the best fit from the catalogue on five criteria: keyboard and ARIA, states, motion under gates 31-31d, the tests and hooks that read its DOM, and the packages it needs. When the source leads, it takes the role and its line adds `· replaces <path>: leads on <criteria> · keep: <every class, id and DOM shape a test or motion hook reads, or the test edits that ship with the swap>`. When the incumbent holds, its line adds `· upgrade checked: <source> trails on <criteria>`, and each behaviour the source does better rides on the inherit line as `· fix: <behaviour>, <source> as the spec`.
- **Packages need approval.** On an INHERIT or EXISTING pass, a source whose code needs an npm package the project's `package.json` does not list (motion or framer-motion, lucide-react, input-otp, vaul, recharts, ...) takes its section 8 port line, which rebuilds that dependency on the project's own motion, icons and native elements, unless the brief approves the package. A source with no port line (kit components, Bencho, BoardUI, TailGrids, HeroUI) fits only once the brief approves the package; the line or walk note names the package. On an OPEN pass the line lists each package it adds.
- **Licence before fit.** A library with no licence is a reference only - read it for the pattern, copy no code. A free tier licensed for personal use only never goes into client or production work. A free tier with conditions is code under those conditions, and the line states them: shadcn studio's MIT + Commons Clause (no sale or redistribution of the components, no competing product), transitions.dev's terms (keep the comment, never repackaged into a kit), Relume's single-use licence (no redistribution, no competing product). A catalogue row whose Licence says "check before use" is no fit until its licence text is read and recorded on the line. Per-library facts: [libraries.md](libraries.md); each catalogue row's Licence column gives the short form.
- **Motion recipes.** A component whose enter, exit, view change, toggle or loading motion the Design block names may add section 8's motion recipe line beside its own line, on every stack; the Design block's timing and gates 31-31d still rule.
- **Walk notes are optional.** Name the sources checked and why each failed on a test run of this file, or when a passed-over source would surprise the reader.
- **Catalogue, best fit.** For each interactive component in the plan (toast, input, dropdown, node card, upload, picker, chart, ...), look up its role in `D:\jc-ui-kit\CATALOG.md` - one index of JC's kit and every library: the default view holds the `core` and `standard` rows, and `archive` rows stay listed in `D:\jc-ui-kit\CATALOG-archive.md` - then open the source file each candidate row links to (the kit README, [bencho.md](bencho.md), [affectui.md](affectui.md), [reui.md](reui.md) or [libraries.md](libraries.md)) for its rules. Weigh every candidate this stack can take (its section below says which come in as code, as a port, or only as a checklist) on fit for the role - the features and states it needs, keyboard and ARIA, the packages it adds, the porting it needs, its licence - and write one line: take a `core` row when one covers the features and states the role needs, a `standard` row when no core row does, and an archive row only when nothing else fits, the line saying which archive row and why. Core sources: affectUI, Arc, beUI, HextaUI, overtrue/ui, Dashboardblocks, JC's kit, Phosphor, and ReUI's in-house Data Grid and Filters items. Ranking words left in the per-source files ("stays first", "the kit component wins") give way to this rule, while their facts, gaps and licence clauses still hold. A half fit counts as no fit. Charts go to `dataviz` first (step 1).
- **Pro** - any paid tier: affectUI, Arc, beUI, HextaUI, Dashboardblocks, Efferd, ReUI, Bencho, BoardUI, TailGrids, HeroUI, shadcn studio, transitions.dev, Kobra, Cue+, Uberdesigner, HorizonX, uibrik - only when JC owns it. Record here the paid tiers you own, with the date confirmed; a recorded tier needs no further confirmation, and the line states that; for every other paid tier ownership is unknown, so it needs the brief to confirm JC owns it, and the line states that confirmation. Ownership loosens no source's own gate, and Pro code lives only in the project that uses it. Without ownership a Pro-only match is no fit, and a Pro best fit that cannot be used - not owned, or owned but failing its source's own gate - takes the Pro fallback (section 9): a free close fit, else an REA clean-room rebuild when the source's terms check gives its Pro items a CLEAR verdict, else build fresh. Bencho Pro: section 7. ReUI Pro has a second gate, the verified licence: section 6. Kobra Pro: section 8. Every other paid tier: its licence clause in section 8's table, from libraries.md.
- **Feel 1:1, brand from the block (JC, 2026-11-07).** A component taken from a source keeps its motion and interaction exactly as the source ships it: durations, delays, easings, springs, transforms, staged sequences, gestures, digit rolls, layout animation, hover and press feedback. Only brand changes: colours, fonts, radii, spacing, icons and copy come from this block's Tokens (or the inherited ones). Demo data, demo timers and demo-only flourishes (sounds, remote avatars) go; motion stays. A source without a reduced-motion path gets one added, leaving the default motion untouched. The block's motion tokens and gates 31-31d govern only what is built fresh. The builder proves it with `python -I D:\jc-ui-kit\scripts\motion-diff.py <upstream file> <built file>` per sourced component, exit 0. No source's own colours, fonts or spacing override the block. Contrast and the interactive states still bind on every component.
- **Feel picks the source for interactive pieces.** Buttons, toggles, tabs, menus, selects, drawers, dialogs, toasts, tooltips and inputs take a core source with authored motion first - Arc, beUI, affectUI - weighing the porting as a cost, not a reason to skip it; structure pieces (tables, layouts, charts, page blocks) take the shadcn-native core (Dashboardblocks, HextaUI, overtrue/ui). For the 1:1 feel, approve the source's motion package (`motion`) rather than porting it away whenever the brief allows.
- **Behaviour reference.** A line whose role has a kit counterpart may carry that kit README's Motion and Keyboard sections as a behaviour reference beside its own source; where the two differ (thresholds, durations, key maps), the Design block's Gates decide, not the source.
- **Done** when every interactive component in the plan has its line, or the slot reads `none` because the surface has none.

## 3. React + Tailwind, no shadcn

Section 2's candidates (the Uiverse element and its copy line, the Phosphor SVGs and the Relume free block, whose line replaces its relume-ui imports, need no shadcn), except that ReUI, shadcn primitives and the registry libraries in section 8 install only through shadcn: a library candidate takes section 8's port line (written in Tailwind) unless the brief approves adding shadcn (a Bklit chart is the exception: it takes section 8's chart line only with shadcn approved, else a behaviour spec on the build-fresh line, because its visx and `motion` code cannot be ported). The ReUI or shadcn-primitive candidate depends on the pass:

- **OPEN pass.** The ReUI or shadcn-primitive line opens with the setup: `<component>: <ReUI | shadcn> <name> · run npx shadcn@latest init first, flavour Radix UI (Base UI when package.json already lists a Base UI package) · init writes components.json, a cn() helper, and theme variables plus a base layer (body background and text, border colour) into the entry stylesheet: point those variables at this block's Tokens`, then carries section 6's free line from `npx shadcn@latest add <@reui/<slug> | name>` on, its flavour the one given to init (and the install clause for a data grid). This skill's decision: Radix UI is the default flavour because it is shadcn's long-standing default and the ReUI data-grid docs this file cites are its Radix pages.
- **INHERIT or EXISTING pass.** `shadcn init` rewrites the incumbent's global stylesheet (its base layer sets body background and text: ui.shadcn.com/docs/installation/manual.md lines 189-194), a durable system change that needs the user's approval and is its own task (step 3). Only when the brief approves adding shadcn does the line take the OPEN form, stating "shadcn approved in the brief". Without that: `<component>: no ReUI install (React + Tailwind, no shadcn; init would rewrite the incumbent's globals) · build fresh in Tailwind on <engine> · <ReUI | shadcn> <name> as the feature checklist: <its features from reui.md>`, plus section 6's build clause for a data grid.

### 4b. Kit, integration variant (INHERIT or EXISTING pass)

The greenfield root setup imports `styles\base.css`, which sets the body's type (14px/20px), ground and ink, a global `:focus` reset and ring, scrollbar styling, `::selection` and global box-sizing; `tokens\tokens.css` sets `color-scheme` on `:root`. Mapping `--kit-*` values cannot undo those, so an established surface takes the kit this way:

`<component>: kit <Name>, integration variant · D:\jc-ui-kit\components\<Name>\README.md · copy the component folder plus the component folders and lib\ files its Copy these list names, keeping the kit layout (components\, lib\, tokens\ side by side) · npm: each package the copied files import that package.json lacks (kit components import framer-motion and lucide-react): approved in the brief, or the walk note names them and the role goes to the next-best fit · never copy or import styles\base.css, even where the Copy these list names it; skip README steps 3's fonts, 5 and 8 - the incumbent's global styles, fonts and theme switching stay exactly as they are · tokens: copy tokens\tokens.css with its colour, font, radius and spacing values pointed at the incumbent's own tokens (--kit-ink: var(<incumbent token>)), its color-scheme lines and html[data-theme="dark"] block removed, so the incumbent's theme carries the kit; motion durations, curves and layers stay as the kit sets them · keep README step 4's initModality() (it only sets <html data-modality>), and steps 6 and 7 where they apply (the <Toaster /> and <TooltipLayer /> mounts, the Drawer's inert root) · bring across, into one kit-integration.css imported after the incumbent's globals, only these base.css rules: <each rule below that applies, written out> · nothing in kit-integration.css targets body, html, *, :focus or ::selection unscoped`

The base.css rules a component may need - take each one its copied files call for:

- **Scroll lock**, when `lib\scrollLock.ts` is copied (Drawer, Palette): `body[data-kit-scroll-lock] { overflow: hidden; }` - an attribute rule, inert until a kit layer locks.
- **Press timing**, when a copied CSS file reads `--kit-press-dur` (Button, Dropdown, StepChain, Tabs, and every component whose Copy these list names Button): `:root { --kit-press-dur: 0ms; }` and `html[data-modality="pointer"] { --kit-press-dur: var(--kit-dur-press); }`.
- **Focus ring**, only when the incumbent has no `:focus-visible` style of its own: `:focus-visible { outline: 2px solid var(--kit-focus); outline-offset: 2px; }` scoped under the component's root class. base.css's `:focus { outline: none; }` never comes across; when the incumbent has a ring, the kit component uses it.
- **Reduced motion**: from base.css's `@media (prefers-reduced-motion: reduce)` block, the rule for each piece brought across - `.kit-spin { animation: none; }`, `.kit-swap-in { animation-name: kit-swap-in-rm; }`, `html[data-modality="pointer"] { --kit-press-dur: 0ms; }`.
- **Kit utilities and keyframes** the copied files use (`.kit-sr-only`, `.kit-tnum`, `.kit-mono`, `.kit-kbd`, `.kit-spin`, `.kit-content-fade`, `.kit-swap-in`, with their `@keyframes`): class-scoped, copied as they are.
- **Box-sizing**, when the incumbent does not already set border-box globally: `*, *::before, *::after { box-sizing: border-box; }` scoped under the component's root class.

Every other base.css rule stays out.

**A kit lib file without a component** (e.g. `lib\modality.ts` to make keyboard-started motion instant): `<role>: kit lib <file>, integration variant · copy D:\jc-ui-kit\lib\<file> to <project path>\jc-kit\lib\<file> unchanged except one header comment naming its source and today's date · copy no component folder and no other lib file · no styles\base.css, no tokens\tokens.css · its init call (initModality() for modality.ts) in <entry file> before the root renders · the rules it needs written in this block's own tokens, not base.css's · npm: <none, or each package it imports>`

## 6. ReUI lines

**Data grid, install clause.** Every line that installs a ReUI data grid - the in-house `@reui/data-grid`, a `c-data-grid-*` example, or a Pro data-grid block - adds, word for word:

`· keyboard needs all three, or the grid ships as an ARIA grid with mouse selection and no arrow keys: tableLayout={{ cellSelection: true }} on <DataGrid>; <DataGridCellSelection /> mounted once inside <DataGridContainer>, next to the table; cellSelectionFeature kept in any custom tableFeatures bundle (without it the flag is silently inert) · column virtualisation stays off while cellSelection is on (unsupported upstream) · writable columns: <each column that sets meta.cellEdit, or none: the grid is read-only> · verify by keyboard alone: <the grid walk>`

Source: reui.io/docs/components/radix/data-grid.md (curl, 2026-10-19) - line 120 (`cellSelectionFeature` gates the spreadsheet layer), 843 (column window with `cellSelection` unsupported), 849-859 (`DataGridCellSelection` is the keyboard controller, mounted inside `DataGridContainer`; the flag alone wires mouse selection only), 863-886 (ARIA grid and keyboard map).

**Data grid, build clause.** Every line that builds a data grid fresh with ReUI as its checklist (sections 3, 4 and 5) adds:

`· keyboard grid navigation, ReUI's map as the target: role="grid" with aria-rowindex/aria-colindex, aria-sort on sortable headers and aria-selected on body cells; DOM focus stays on the table while aria-activedescendant tracks the focused cell; arrows move it, Shift+arrows extend, Ctrl/Cmd+arrows jump to the edge, Home/End and PageUp/PageDown jump, Enter or F2 edits or activates the cell's control, Esc clears the selection or returns focus from an in-cell control to the grid, Tab/Shift+Tab step across cells and leave at the grid's edge; header controls are reached with Tab · verify by keyboard alone: <the grid walk>`

**The grid walk**, written out on both clauses and repeated in the block's Verify: `Tab to the grid; arrows move the focused cell and a screen reader announces each move; Shift+arrows extend the range; Home/End and PageUp/PageDown jump; Enter or F2 opens the editor or activates an in-cell control; Esc returns focus to the grid; Tab at the grid's edge leaves it; header sort and filter controls are reached with Tab`.

1. The brief confirms JC owns ReUI Pro or Ultimate, and the line states that confirmation.

## 9. Pro fallback

A Pro item is the best fit for a role and cannot be used - not owned (not one of the six Pro tiers and memberships section 1 records, and the brief does not confirm JC owns it), or owned but failing its source's own gate (ReUI section 6, Bencho section 7). Take the first branch that holds and write its line:

1. **Free close fit.** The best free row for the role in `D:\jc-ui-kit\CATALOG.md` covers the features and states the role needs: write that row's line, by its source's section. A free close fit always comes before a rebuild.
2. **REA rebuild, Pro verdict CLEAR.** The Pro item's source has a terms check that explicitly covers clean-room recreation of its paid items: a separate `Pro verdict: CLEAR` line in `C:\Users\<you>\rea-lab\targets\ui-kits\<slug>\TOS.md` (or a Pro-specific terms check beside it), read from the Pro licence or terms text and quoting every paid-licence clause it relied on. A site verdict written for the free items never counts, so with today's TOS.md files every source's Pro items start at `terms check pending: <slug> (Pro)`. A Pro licence that forbids derivative works or competing products, or says everything beyond the free list requires a licence, is RESTRICTED: branch 3. With the Pro verdict CLEAR, write the rebuild line below, and the walk note asks JC for an item-scoped REA job: `<Source> <item>` named, its Pro verdict path, this block's Design tokens attached as the styling target, behaviour-only scope - set up by the owner of `C:\Users\<you>\rea-lab\targets\ui-kits`. That folder's runner has no item-scoped mode today: it runs the fixed study job (six free-visible components per site, built in the site's measured tokens), so it is not the route for this request. The job keeps the clean-room steps: REA capture of the item -> SPEC.md -> a builder writes code from SPEC.md only -> copied-code check CLEAN -> review. While the Pro verdict is pending, the walk note asks JC for the Pro terms check first, and only a Pro verdict of CLEAR lets the rebuild go ahead - any other verdict moves the role to branch 3. A rebuild for client work recreates behaviour, not brand: it takes this block's Design tokens and states and is never a pixel copy of the original; the fidelity look-alikes already catalogued (the `reaui` rows, tier reference) stay study-only. The finished rebuild joins `D:\jc-ui-kit\catalog\reaui.json` with tier `free`, licence `JC clean-room REA rebuild - terms CLEAR (<TOS.md path>); behaviour only, project styling`, and `upstream` set to the Pro original's id.
3. **Pro verdict RESTRICTED or UNKNOWN, or no licence.** No rebuild and no other workaround: `<component>: build fresh · <Source> <item> (Pro) as a look-only reference`, planned as usual.

**Rebuild line** (strict): `<component>: REA rebuild of <Source> <item> (Pro, not owned) · Pro verdict CLEAR: <TOS.md path> | terms check pending: <slug> (Pro) · behaviour from SPEC.md, this block's Design tokens, no copied code · until it lands: <the best free candidate's full line, or build fresh>`.
