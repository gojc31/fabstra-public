# Components - step 5(c)

Step 5(c) runs this file at every scope - PAGE, SCREEN, COMPONENT, EXISTING - on OPEN and INHERIT passes alike, whenever the plan has interactive components. It names the stack, picks the best-fitting source for each interactive component from `D:\jc-ui-kit\CATALOG.md`, and writes one line per component into the blueprint's `Components:` slot.

Builders never load skills, so every line carries all of its instructions itself. Write each shape below out in full on the line - its known gaps, keyboard clause, verify walk and licence included - never a pointer back to this file. The slot may open with one `States:` preamble holding the state rules every line shares (focus ring, hover, active, disabled); each line then writes only the states that differ.

## 1. The stack, and what binds on every stack

Name the stack first, from the brief or the project. Five signals, each read on its own:

| Signal | Present when |
| --- | --- |
| **React** | `package.json` lists `react` and the surface renders through it (Next.js, Remix, Vite React). Otherwise name the framework: SvelteKit, Svelte, Nuxt, Vue, Astro, plain HTML |
| **Tailwind** | `tailwindcss` in `package.json`, a `tailwind.config.*`, or `@import "tailwindcss"` / `@tailwind` in the entry stylesheet |
| **shadcn** | a `components.json` at the root of the app or package the UI installs into (shadcn-svelte and shadcn-vue write one too; without React the project still takes section 5) |
| **Astryx** | `@astryxdesign/core` in `package.json` (Meta's Astryx design system; its CSS imports `@astryxdesign/core/reset.css` and `astryx.css` and a `<Theme>` provider usually sit in the app root) |
| **Lenso** | `@lenso/ui` in `package.json` (the Lenso UI design system; its theme CSS `@lenso/tokens/styles.css` and a `<ThemeScope>` usually sit in the app root) |

A Tailwind signal proves neither React nor shadcn: a SvelteKit or Nuxt app carries the same Tailwind signals. With no project yet and a brief that does not say, ask that one question: which framework, and Tailwind or plain CSS. When the Astryx signal is present, also record the Tailwind major (3 or 4, from the `tailwindcss` version in `package.json`), because section 10's setup differs by it. A StyleX signal alone (`@stylexjs/stylex` in `package.json`) routes nowhere: not into section 10, not into section 11.

| Stack | Section |
| --- | --- |
| React + Astryx, with or without Tailwind or shadcn (the Astryx signal present, or an OPEN pass that adopts Astryx by section 10's rule) | section 10 - it takes precedence over the rows below for every role the project does not already ship |
| React + Lenso (the Lenso signal present, or an OPEN pass that adopts Lenso by section 11's rule) | section 11 - it takes precedence over the rows below for every role the project does not already ship; Lenso and Astryx never mix in one project |
| React + Tailwind + shadcn | section 2 |
| React + Tailwind, no shadcn | section 3 |
| React + plain CSS | section 4 |
| Any other framework, Tailwind or plain CSS | section 5 |

The blueprint's `Stack:` line names every signal and where each came from, e.g. `Stack: React + Tailwind + shadcn · from package.json react, @import "tailwindcss" in src/index.css, components.json`; with the Astryx signal it adds Astryx, its version and the Tailwind major, e.g. `Stack: React 19 + Astryx 0.7.11 + Tailwind 4 + no shadcn · from package.json react, @astryxdesign/core, tailwindcss ^4`; with the Lenso signal it adds Lenso and its version, e.g. `Stack: React 19.2 + Lenso 0.10.0 + no Tailwind + no shadcn · from package.json react, @lenso/ui`.

On every stack:

- **Inherit before invent.** When the project already has its own component for the role, the line is `<component>: inherit <path>`, ahead of every source - on a shadcn project that includes its own shadcn or ReUI components. A native control the project already uses (`<input type="date">`, `month`, `number`, `<select>`) is the incumbent too. On an EXISTING redesign or a restyle, write the restyled form: `<component>: inherit <path>, restyled · restyle: <what changes> · states: <default, hover, focus-visible, active, disabled, loading, error, success> · keep: <every class, id and DOM shape a test or motion hook reads>`. An incumbent that serves the role stays inherit even when it fails a gate as built; the Design block fixes its motion and states. It falls to the next source when it cannot serve the role, or on an **upgrade brief** - one that asks to take a library component where it beats the incumbent. An upgrade brief compares, per role, the incumbent with the best fit from the catalogue on five criteria: keyboard and ARIA, states, motion under gates 31-31d, the tests and hooks that read its DOM, and the packages it needs. When the source leads, it takes the role and its line adds `· replaces <path>: leads on <criteria> · keep: <every class, id and DOM shape a test or motion hook reads, or the test edits that ship with the swap>`. When the incumbent holds, its line adds `· upgrade checked: <source> trails on <criteria>`, and each behaviour the source does better rides on the inherit line as `· fix: <behaviour>, <source> as the spec`.
- **Packages need approval.** On an INHERIT or EXISTING pass, a source whose code needs an npm package the project's `package.json` does not list (motion or framer-motion, lucide-react, input-otp, vaul, recharts, ...) takes its section 8 port line, which rebuilds that dependency on the project's own motion, icons and native elements, unless the brief approves the package. A source with no port line (kit components, Bencho, BoardUI, TailGrids, HeroUI) fits only once the brief approves the package; the line or walk note names the package. On an OPEN pass the line lists each package it adds.
- **Licence before fit.** A library with no licence is a reference only - read it for the pattern, copy no code. A free tier licensed for personal use only never goes into client or production work. A free tier with conditions is code under those conditions, and the line states them: shadcn studio's MIT + Commons Clause (no sale or redistribution of the components, no competing product) and transitions.dev's terms (keep the comment, never repackaged into a kit). A catalogue row whose Licence says "check before use" is no fit until its licence text is read and recorded on the line. Per-library facts: [libraries.md](libraries.md); each catalogue row's Licence column gives the short form.
- **Motion recipes.** A component whose enter, exit, view change, toggle or loading motion the Design block names may add section 8's motion recipe line beside its own line, on every stack; the Design block's timing and gates 31-31d still rule.
- **Walk notes are optional.** Name the sources checked and why each failed on a test run of this file, or when a passed-over source would surprise the reader.
- **Catalogue, best fit.** For each interactive component in the plan (toast, input, dropdown, node card, upload, picker, chart, ...), look up its role in `D:\jc-ui-kit\CATALOG.md` - one index of JC's kit and every library: the default view holds the `core` and `standard` rows, and `archive` rows stay listed in `D:\jc-ui-kit\CATALOG-archive.md` - then open the source file each candidate row links to (the kit README, [bencho.md](bencho.md), [affectui.md](affectui.md), [reui.md](reui.md) or [libraries.md](libraries.md)) for its rules. Weigh every candidate this stack can take (its section below says which come in as code, as a port, or only as a checklist) on fit for the role - the features and states it needs, keyboard and ARIA, the packages it adds, the porting it needs, its licence - and write one line: take a `core` row when one covers the features and states the role needs, a `standard` row when no core row does, and an archive row only when nothing else fits, the line saying which archive row and why. Core sources: affectUI (free + Pro) first, then Arc, HextaUI, overtrue/ui, Dashboardblocks, Detent, JC's kit, Phosphor, and ReUI's in-house Data Grid and Filters items. Ranking words left in the per-source files ("stays first", "the kit component wins") give way to this rule, while their facts, gaps and licence clauses still hold. A half fit counts as no fit. Charts go to `dataviz` first (step 1). On the Astryx stack, section 10's order replaces this weighing for every role the project does not already ship.
- **affectUI first, every surface (JC, 2026-11-26: "Everything").** affectUI (free + Pro) is the first source for every role it covers, on app UI and on landing or marketing surfaces alike, except when the project runs on a whole-system stack (Astryx or Lenso): there that stack's own components come first and affectUI fills only the roles that stack lacks (a free affectUI item by the port line; an affectUI Pro item is no fit there). Elsewhere it comes first on every stack that takes it as code (sections 2-4; a Pro item only by section 8's affectUI row: the registry install on React 19, kept as delivered). Arc, HextaUI, overtrue/ui, Dashboardblocks, Detent, JC's kit, ReUI and every other source fill only a role affectUI lacks or half-covers - for example a heavy data grid with filters, paging, virtualisation or pivot goes to ReUI's free data grid or TanStack (Arc Pro is not owned), and a landing section beyond affectUI's 15 blocks (2 free, 13 Pro) goes to the next fit. When a non-affectUI row wins, the weighing line names the gap: `· affectUI gap: <what affectUI's nearest item lacks for this role, or "no affectUI item for this role">`. Brand over kit still holds: the project's brand guide and the Design block's Tokens outrank affectUI's default theme, which takes them through `--aui-*` only. On the whole-system stacks (sections 10 and 11) the free item's `--aui-*` values point at that stack's tokens; Pro is no fit there because those stacks take no registry-library install and Pro is never ported. On a section 5 framework affectUI is a checklist only, like every React source.
- **Astryx off its stack.** On sections 2-5 the catalogue's Astryx rows are a behaviour checklist only (`· Astryx <Name> as the behaviour spec: <what its docs specify>` on the chosen line): an Astryx component, even through its shadcn registry (astryx.atmeta.com/shadcn/registry.json), installs `@astryxdesign/core` and `@stylexjs/stylex` and adds Astryx's own reset and component CSS layers, which adopts the whole system. It comes in as code only when the brief switches the project to Astryx; the project then takes section 10.
- **Lenso off its stack.** On sections 2-5 the catalogue's Lenso rows are a behaviour checklist only (`· Lenso <Name> as the behaviour spec: <what its docs specify>` on the chosen line), primitives and the Photos template included: a Lenso component adopts StyleX compilation, the `@lenso/tokens` theme and the `@lenso/glass` layer, which adopts the whole system. It comes in as code only when the project is on Lenso or adopts it; the project then takes section 11.
- **Pro** - any paid tier - only when it is recorded as owned. affectUI Pro is recorded as owned and no other paid tier is; affectUI (free + Pro) is the first-ranked core source for every surface, app UI and landing alike; Pro code lives only in the project that uses it, never in this kit or a skill folder. affectUI Pro items are catalogued beside the free ones and take section 8's registry line (a component, block, illustration or motion item) or its screen line (a whole page from a Pro app screen), each carrying the affectUI Pro licence clause. Every other paid tier - HorizonX, Uberdesigner, Arc Pro, ReUI Pro, beUI, Bencho, Kobra and 21st.dev included - stays not owned, so for those sources lines come from free tiers only - HorizonX's 5 free Drops and every other free source, with Uberdesigner's free templates as a personal-use reference only (section 8); the HorizonX and Uberdesigner Pro rows still in the catalogue are not owned and never picked, and every other paid tier is uncatalogued (cut 2026-11-11). A paid item enters a plan only when a brief names it and confirms it was bought, and the line states that confirmation and cites that source's dated terms link in libraries.md (the bought tier's rows are surveyed back into the catalogue afterwards, as a follow-up the line names). Ownership loosens no source's own gate, and Pro code lives only in the project that uses it. Without ownership a Pro-only match is no fit, and a Pro best fit that cannot be used - not owned, or owned but failing its source's own gate - takes the Pro fallback (section 9): a free close fit, else an REA clean-room rebuild when the source's terms check gives its Pro items a CLEAR verdict, else build fresh.
- **Feel 1:1, brand from the block (JC, 2026-11-07).** A component taken from a source keeps its motion and interaction exactly as the source ships it: durations, delays, easings, springs, transforms, staged sequences, gestures, digit rolls, layout animation, hover and press feedback. Only brand changes: colours, fonts, radii, spacing, icons and copy come from this block's Tokens (or the inherited ones). Demo data, demo timers and demo-only flourishes (sounds, remote avatars) go; motion stays. A source without a reduced-motion path gets one added, leaving the default motion untouched. The block's motion tokens and gates 31-31d govern only what is built fresh. The builder proves it with `python -I D:\jc-ui-kit\scripts\motion-diff.py <upstream file> <built file>` per sourced component, exit 0; an Astryx or Lenso component imported from its package has no copied file, so each takes its own section's proof instead (section 10 or section 11: exact version pin, no motion override, the Verify walk). No source's own colours, fonts or spacing override the block. Contrast and the interactive states still bind on every component.
- **Feel picks the source for interactive pieces.** affectUI takes every role it covers first, interactive or structure (the affectUI-first rule above). Where affectUI lacks or half-covers a role, buttons, toggles, tabs, menus, selects, drawers, dialogs, toasts, tooltips and inputs take a core source with authored motion next - Arc - weighing the porting as a cost, not a reason to skip it; structure pieces (tables, layouts, charts, page blocks) take the shadcn-native core (Dashboardblocks, HextaUI, overtrue/ui). For the 1:1 feel, approve the source's motion package (`motion`) rather than porting it away whenever the brief allows. On the Astryx stack, Astryx's own component takes the role first, interactive or structure (section 10); on the Lenso stack, Lenso's own component does (section 11).
- **Behaviour reference.** A line whose role has a kit counterpart may carry that kit README's Motion and Keyboard sections as a behaviour reference beside its own source; where the two differ (thresholds, durations, key maps), the Design block's Gates decide, not the source.
- **Done** when every interactive component in the plan has its line, or the slot reads `none` because the surface has none.

## 3. React + Tailwind, no shadcn

Section 2's candidates (the Phosphor SVGs need no shadcn), except that ReUI, shadcn primitives and the registry libraries in section 8 install only through shadcn: a library candidate takes section 8's port line (written in Tailwind) unless the brief approves adding shadcn. The ReUI or shadcn-primitive candidate depends on the pass:

- **OPEN pass.** The ReUI or shadcn-primitive line opens with the setup: `<component>: <ReUI | shadcn> <name> · run npx shadcn@latest init first, flavour Radix UI (Base UI when package.json already lists a Base UI package) · init writes components.json, a cn() helper, and theme variables plus a base layer (body background and text, border colour) into the entry stylesheet: point those variables at this block's Tokens`, then carries section 6's free line from `npx shadcn@latest add <@reui/<slug> | name>` on, its flavour the one given to init (and the install clause for a data grid). This skill's decision: Radix UI is the default flavour because it is shadcn's long-standing default and the ReUI data-grid docs this file cites are its Radix pages.
- **INHERIT or EXISTING pass.** `shadcn init` rewrites the incumbent's global stylesheet (its base layer sets body background and text: ui.shadcn.com/docs/installation/manual.md lines 189-194), a durable system change that needs the user's approval and is its own task (step 3). Only when the brief approves adding shadcn does the line take the OPEN form, stating "shadcn approved in the brief". Without that: `<component>: no ReUI install (React + Tailwind, no shadcn; init would rewrite the incumbent's globals) · build fresh in Tailwind on <engine> · <ReUI | shadcn> <name> as the feature checklist: <its features from reui.md>`, plus section 6's build clause for a data grid.

### 4b. Kit, integration variant (INHERIT or EXISTING pass)

The greenfield root setup imports `styles\base.css`, which sets the body's type (14px/20px), ground and ink, a global `:focus` reset and ring, scrollbar styling, `::selection` and global box-sizing; `tokens\tokens.css` sets `color-scheme` on `:root`. Mapping `--kit-*` values cannot undo those, so an established surface takes the kit this way:

`<component>: kit <Name>, integration variant · D:\jc-ui-kit\components\<Name>\README.md · copy the component folder plus the component folders and lib\ files its Copy these list names, keeping the kit layout (components\, lib\, tokens\ side by side) · npm: each package the copied files import that package.json lacks (kit components import framer-motion and lucide-react): approved in the brief, or the walk note names them and the role goes to the next-best fit · never copy or import styles\base.css, even where the Copy these list names it; skip README steps 3's fonts, 5 and 8 - the incumbent's global styles, fonts and theme switching stay exactly as they are · tokens: copy tokens\tokens.css with its colour, font, radius and spacing values pointed at the incumbent's own tokens (--kit-ink: var(<incumbent token>)), its color-scheme lines and html[data-theme="dark"] block removed, so the incumbent's theme carries the kit; motion durations, curves and layers stay as the kit sets them · keep README step 4's initModality() (it only sets <html data-modality>), and steps 6 and 7 where they apply (the <Toaster /> and <TooltipLayer /> mounts, the Drawer's inert root) · bring across, into one kit-integration.css imported after the incumbent's globals, only these base.css rules: <each rule below that applies, written out> · nothing in kit-integration.css targets body, html, *, :focus or ::selection unscoped`

The base.css rules a component may need - take each one its copied files call for:

- **Scroll lock**, when `lib\scrollLock.ts` is copied (Drawer, Palette): `body[data-kit-scroll-lock] { overflow: hidden; }` - an attribute rule, inert until a kit layer locks.
- **Press timing**, when a copied CSS file reads `--kit-press-dur` (Button, Dropdown, StepChain, Tabs, and every component whose Copy these list names Button): `:root { --kit-press-dur: 0ms; }` and `html[data-modality="pointer"] { --kit-press-dur: var(--kit-dur-press); }`.
- **Focus ring**, only when the incumbent has no `:focus-visible` style of its own: `:focus-visible { outline: 2px solid var(--kit-focus); outline-offset: 2px; }` scoped under the component's root class. base.css's `:focus { outline: none; }` never comes across; when the incumbent has a ring, the kit component uses it.
- **Reduced motion**: from base.css's `@media (prefers-reduced-motion: reduce)` block, the rule for each piece brought across - `.kit-spin { animation: none; }`, `.kit-swap-in { animation-name: kit-swap-in-rm; }`, `html[data-modality="pointer"] { --kit-press-dur: 0ms; }`.
- **Kit utilities and keyframes** the copied files use (`.kit-sr-only`, `.kit-tnum`, `.kit-mono`, `.kit-kbd`, `.kit-spin`, `.kit-content-fade`, `.kit-swap-in`, with their `@keyframes`): class-scoped, copied as they are.
- **Box-sizing**, when the incumbent does not already set border-box globally: `*, *::before, *::after { box-sizing: border-box; }` scoped under the component's root class.

Every other base.css rule stays out.

**A kit lib file without a component** (e.g. `lib\modality.ts` to make keyboard-started motion instant): `<role>: kit lib <file>, integration variant · copy D:\jc-ui-kit\lib\<file> to <project path>\jc-kit\lib\<file> unchanged except one header comment naming its source and today's date · copy no component folder and no other lib file · no styles\base.css, no tokens\tokens.css · its init call (initModality() for modality.ts) in <entry file> before the root renders · the rules it needs written in this block's own tokens, not base.css's · npm: <none, or each package it imports>`
